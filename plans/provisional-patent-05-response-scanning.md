## TECHNICAL FIELD

The present disclosure relates generally to cybersecurity and, more specifically, to systems and methods for intercepting and scanning the output responses generated by artificial intelligence (AI) models — including large language model (LLM) completions, agent action results, and tool invocation outputs — to detect personally identifiable information (PII) leakage, secret/credential exposure, factual hallucinations, and toxic or harmful content before the response is delivered to the end user.

## BACKGROUND

Most AI security systems focus on input validation — scanning what users send to AI models (prompt injection detection, data exfiltration prevention). However, the output of AI models poses an equal and distinct set of risks that existing systems do not address:

1. **PII Leakage in Responses:** AI models may regurgitate training data containing PII. An LLM asked to "write an email about a customer named John" may generate a response containing a real SSN, email address, or phone number from its training corpus. The model may also aggregate and infer PII from context provided across multiple prompts.

2. **Secret/Credential Exposure in Responses:** AI models, particularly coding assistants, may generate responses containing real API keys, passwords, or connection strings — either from training data memorization or from context provided in the conversation. A code completion tool may suggest a connection string with a real password from a public repository it was trained on.

3. **Hallucination Detection:** AI models generate plausible but false information ("hallucinations") that may have serious consequences. An AI agent may claim to have executed a database query successfully when it did not, or may provide incorrect medical/legal/financial information with high confidence. Unlike PII or secrets (which can be detected with pattern matching), hallucinations require contextual analysis of the response against the expected output.

4. **Toxic/Harmful Content:** AI models may generate toxic, offensive, or harmful content despite safety guardrails. A jailbroken model may produce content that violates organizational policies, regulatory requirements, or legal standards.

Existing systems do not scan AI model responses for all four categories in a unified pipeline. DLP tools scan the output but lack hallucination detection. Content moderation tools scan for toxicity but lack PII and secret detection. No system unifies all four response-side detection categories for AI model outputs.

What is needed is a system that intercepts AI model responses, applies a unified detection pipeline covering PII, secrets, hallucinations, and toxicity, and blocks or redacts harmful content before delivery to the end user.

## SUMMARY OF THE INVENTION

The present disclosure describes systems and methods for scanning AI model responses for sensitive data, hallucinations, and harmful content. The system comprises: a response interception module configured to intercept AI model responses before delivery to the end user; a PII detection sub-module configured to detect personally identifiable information in response content; a secret detection sub-module configured to detect credentials and API keys in response content; a hallucination detection sub-module configured to identify factually unsupported claims in response content; a toxicity filtering sub-module configured to detect toxic or harmful content; and a response action module configured to block, redact, or permit the response based on detection results.

In one embodiment, the PII detection sub-module applies at least 11 categories of PII patterns to response content, including: names, email addresses, phone numbers, Social Security numbers, credit card numbers, postal addresses, dates of birth, passport numbers, driver's license numbers, healthcare identifiers, and financial account numbers.

In another embodiment, the secret detection sub-module applies at least 17 secret/credential patterns to response content, including: AWS, GCP, Azure, GitHub, GitLab, Slack, Stripe, Twilio, SendGrid, Mailgun, Discord, private keys, database connection strings, OAuth tokens, JWT tokens, bearer tokens, and generic high-entropy strings.

In another embodiment, the hallucination detection sub-module identifies hallucinations by analyzing at least 4 categories: (a) factual claims without supporting evidence, (b) fabricated URLs or citations, (c) assertions about completed actions that were not actually performed, and (d) statistics or numbers that cannot be verified against known sources.

In another embodiment, the toxicity filtering sub-module classifies content into at least 6 categories: (a) hate speech, (b) harassment, (c) violence/threats, (d) self-harm, (e) sexual content, and (f) illegal activities.

## DETAILED DESCRIPTION

### 1. System Architecture

The response scanning system operates as an intermediary between an AI model and the end user (or consuming application). The system intercepts AI model responses — including LLM completions, agent action results, tool invocation outputs, and streaming response chunks — and applies a unified detection pipeline before delivering the response.

### 1.1 Response Interception Module

The response interception module intercepts AI model responses using one or more of:

1. **API Proxy Interception:** The AI client sends requests to the AI model through a proxy. Responses are intercepted at the proxy, scanned, and either delivered or blocked.

2. **Streaming Interception:** For streaming responses (e.g., Server-Sent Events, chunked transfer encoding), the interception module buffers response chunks, applies detection, and releases safe chunks while blocking unsafe ones. Buffering introduces minimal latency (sub-millisecond for pattern matching, configurable window for ML classification).

3. **Local Proxy Interception:** For developer tools (e.g., Copilot, Cursor), the interception module runs as a local proxy on the developer's workstation, intercepting AI tool responses before they are displayed in the IDE.

4. **Browser Extension Interception:** For web-based AI tools (ChatGPT, Claude, Gemini), a browser extension intercepts rendered response content from the DOM before it is displayed to the user.

### 1.2 PII Detection Sub-Module (11 categories)

The PII detection sub-module applies regular expression and pattern matching to response content to detect:

1. **Names:** Full person names using name detection patterns (capitalized word sequences with common first/last name patterns, excluding sentence starts).
2. **Email Addresses:** RFC 5322 compliant email patterns.
3. **Phone Numbers:** International phone number patterns (E.164 format and common local formats for 24+ jurisdictions).
4. **Social Security Numbers:** US SSN patterns with and without formatting.
5. **Credit Card Numbers:** PAN patterns with Luhn checksum validation for Visa, Mastercard, Amex, Discover, JCB.
6. **Postal Addresses:** Street address + city + state/region + postal code patterns for US and international formats.
7. **Dates of Birth:** Date patterns in context indicating birth dates (e.g., "born on", "DOB", "date of birth" followed by date).
8. **Passport Numbers:** US and international passport number patterns.
9. **Driver's License Numbers:** US state-specific and international driver's license patterns.
10. **Healthcare Identifiers:** NPI numbers, Medicare beneficiary identifiers, Medicaid IDs, medical record numbers.
11. **Financial Account Numbers:** Bank account numbers, routing numbers, SWIFT/BIC codes, IBAN numbers.

When PII is detected in a response, the response action module redacts the PII (replacing it with a placeholder like `[REDACTED-EMAIL]`) and delivers the redacted response.

### 1.3 Secret Detection Sub-Module (17 patterns)

The secret detection sub-module applies patterns for:

1. **AWS API Keys:** AKIA*, ASIA* prefixes with 16-character key body.
2. **GCP API Keys:** AIza* prefix, GOOG* service account key patterns.
3. **Azure Keys:** Account key patterns, connection string patterns.
4. **GitHub Tokens:** ghp_*, gho_*, ghs_*, ghu_*, ghr_* prefixes.
5. **GitLab Tokens:** glpat-* prefix.
6. **Slack Tokens:** xox[abprs]-* prefix patterns.
7. **Stripe Keys:** sk_live_*, sk_test_*, pk_live_*, pk_test_*, rk_live_* patterns.
8. **Twilio Keys:** SK* prefix with account SID context.
9. **SendGrid Keys:** SG.* prefix pattern.
10. **Mailgun Keys:** key-* prefix pattern.
11. **Discord Tokens:** Bot token patterns (base64-encoded user ID + timestamp + HMAC).
12. **Private Keys:** PEM blocks for RSA, ECDSA, Ed25519, OpenSSH.
13. **Database Connection Strings:** PostgreSQL (postgres://), MySQL (mysql://), MongoDB (mongodb://), Redis (redis://), MS SQL Server connection URIs.
14. **OAuth Tokens:** Bearer token patterns, access token patterns.
15. **JWT Tokens:** Three-part base64-encoded structure (header.payload.signature).
16. **Bearer Tokens:** Authorization header bearer patterns.
17. **Generic High-Entropy Strings:** Configurable Shannon entropy threshold (default: 4.5 bits/character) with minimum length (default: 32 characters) for detecting unknown credential formats.

When a secret is detected in a response, the response action module redacts the secret and may optionally log a security alert (since AI-generated secrets may indicate training data memorization or sensitive context leakage).

### 1.4 Hallucination Detection Sub-Module (4 categories)

The hallucination detection sub-module analyzes response content for:

1. **Factual Claims Without Evidence:** The module detects claims that assert facts without supporting evidence by analyzing: assertion patterns ("X is Y", "According to [unverifiable source]"), and factual statements about events, statistics, or entities that cannot be verified against known sources. The module maintains a confidence score for factual claims based on: specificity of the claim, presence of supporting qualifiers ("I believe", "approximately", "based on available information"), and whether the claim is testable.

2. **Fabricated URLs or Citations:** The module detects URLs and citations in responses by: extracting URL patterns and citation patterns, checking URLs for structural validity, flagging URLs that use domains known to be frequently hallucinated (e.g., non-existent subdomains on real domains), and flagging citations to non-existent papers/books (by checking against known publication databases when available, or by flagging citations with suspicious author/title combinations).

3. **Assertions About Completed Actions:** The module detects claims that an action was performed when it was not by: comparing the response content to the action log (if available), flagging responses that assert "I have done X" or "The query returned Y rows" when no such action was recorded, and flagging responses that provide specific outputs (e.g., "the result is 42") when the actual action output differs or no action was performed.

4. **Unverifiable Statistics:** The module detects statistics and numbers that cannot be verified by: flagging specific numerical claims (percentages, counts, measurements) in contexts where precision is expected (medical, legal, financial), cross-referencing against known databases when available, and flagging statistics presented without source attribution.

When a hallucination is detected, the response action module may: append a disclaimer ("This response may contain unverified claims"), redact the specific hallucinated content, or block the response entirely (for high-severity hallucinations in regulated contexts such as medical or legal advice).

### 1.5 Toxicity Filtering Sub-Module (6 categories)

The toxicity filtering sub-module classifies response content into:

1. **Hate Speech:** Content that attacks, demeans, or promotes violence against groups based on race, ethnicity, religion, gender, sexual orientation, disability, or nationality. Detected using: keyword patterns for slurs and derogatory terms, pattern combinations (negative sentiment + group references), and ML classification for implicit hate speech.

2. **Harassment:** Content that targets specific individuals with hostile, intimidating, or degrading language. Detected using: patterns for threats and intimidation, second-person hostile address patterns, and repeated negative characterization patterns.

3. **Violence/Threats:** Content that depicts, encourages, or provides instructions for violence. Detected using: weapon-related patterns in instructional context, threat patterns ("I will", "you should" + violent action), and depictions of graphic violence.

4. **Self-Harm:** Content that encourages, provides methods for, or depicts self-harm. Detected using: method description patterns, encouragement patterns, and contextual analysis of self-harm-related terms.

5. **Sexual Content:** Content that is sexually explicit or inappropriate for the organizational context. Detected using: explicit content patterns and organizational policy configurations (which may vary by organization).

6. **Illegal Activities:** Content that provides instructions for illegal activities (drug synthesis, weapons manufacturing, hacking tutorials, fraud instructions). Detected using: instructional patterns for known illegal activity categories and legal/jurisdiction-specific pattern sets.

When toxic content is detected, the response action module blocks the response and logs a security event. For borderline content, the module may flag the content for human review rather than blocking outright.

### 1.6 Response Action Module

The response action module takes one of the following actions based on combined detection results:

1. **Block:** The response is not delivered to the end user. The user receives a message indicating that the AI response was blocked by security policy. A security event is logged.

2. **Redact:** Specific sensitive content within the response is replaced with placeholders. The redacted response is delivered. The redaction is logged.

3. **Flag for Review:** The response is delivered with a warning banner ("This response has been flagged for review: [reason]"). The security team receives a notification.

4. **Permit:** The response is delivered without modification. The transaction may be logged for audit purposes.

### 1.7 Response Scanning vs. Prompt Scanning

The response scanning pipeline is distinct from prompt (input) scanning in several ways:

1. **Different content characteristics:** Responses are longer, more structured, and may contain generated text that follows different patterns than user-written prompts.
2. **Different risk profile:** PII in a prompt is a data exfiltration risk (user sending data to AI). PII in a response is a data exposure risk (AI exposing training data or aggregated PII to user).
3. **Different detection priorities:** Prompt scanning prioritizes data exfiltration. Response scanning prioritizes hallucination, toxicity, and PII exposure.
4. **Different action semantics:** Blocking a prompt prevents the user from sending data. Blocking a response prevents the user from receiving AI-generated content — which may be more disruptive to workflow.
